## 审查顺序与依赖

1. 多个账号均能访问同一文档时，何谓“正确账号”？区分文档归属、访问权限和用户希望使用的操作身份。（Q1，待回答）
2. 绑定的业务单位：品牌、应用、租户、用户及操作身份的关系；同一应用多用户的真实凭证隔离能力。（已决：Q2=A，见 ADR-0001）
3. 自动路由的证据：显式选择、文档级记忆、域名提示、访问能力验证、歧义处理；未知域名与裸 token 的输入边界。（已决：Q3 输入契约 + Q4 能力探测）
4. 路由与执行的一致性：账号重登、配置改名、权限变化、URL 与实际 argv 目标不一致、执行时覆盖 profile/as 参数。
5. 操作范围和授权：读写权限分别验证、应用身份回退、确认与具体请求绑定，不能仅依赖 CLI 高风险门禁。
6. 写入可靠性：并发修改、预览与提交之间变化、超时后结果未知、部分成功、重试与幂等、批量跨账号操作。
7. 绑定生命周期：创建应用与用户授权分离；授权流程恢复；插件解绑与删除用户已有 CLI profile 分离。
8. 插件集成与范围：工具是否必须经过路由、已有 lark-* skills 的直接 CLI 路径、首版可用 UI 与文档修改验收。
9. 数据生命周期：文档级记忆失效、跨 DSH 配置共享、审计脱敏、缓存并发与持久化。

以上为待审查项，不代表已定实现方案。后续问题随用户回答调整顺序。

## Q1：同一文档可被多个账号访问

场景：绑定公司账号 A、个人账号 B；公司文档分享给 B，因此两个账号都可编辑。链接只能提示品牌或资源，不能唯一确定用户想用哪个身份。

原草案问题：按唯一 ready 账号自动选中会将登录状态当作身份选择依据；域名匹配也只能产生候选，不能证明它是期望的操作身份。文档属于租户 X，不意味着必须由 X 内某个特定账号执行。

建议（待用户回答）：先尊重本次显式指定，其次文档级的已确认账号偏好；首次多账号歧义时让用户选择并可记住。某账号失效不自动改用另一账号写入，允许修复原绑定或由用户明确改选。

决定：用户选择 A（2026-10-22）。本次显式指定优先，其次文档级已确认账号偏好；首次歧义询问并可记住。原账号失效时不自动改用另一账号写入，修复原绑定或由用户明确改选。空间/租户默认规则尚未批准。

## 证据状态更正

已通过官方 v1.0.76 源码核实：profile add 禁止重复 App ID；token 存储键为 App ID + 用户 open_id，不包含 profile 名。已更正 design.md §2。依据：https://github.com/larksuite/cli/blob/v1.0.76/cmd/profile/add.go 与 https://github.com/larksuite/cli/blob/v1.0.76/internal/auth/token_store.go 。进一步源码证据：cmd/auth/login.go 的 syncLoginUserToProfile 将 profile 用户列表写成单元素，新用户登录会删除旧用户 token；internal/core/config.go 使用 Users[0] 作为有效用户。因此通过现有正式 profile/login 路径无法为同一应用同时维持多个登录用户。未进行真实双用户登录实验；不通过手工复制配置或全局切换用户来假装独立。来源：https://github.com/larksuite/cli/blob/v1.0.76/cmd/auth/login.go 与 https://github.com/larksuite/cli/blob/v1.0.76/internal/core/config.go 。

## Q4：歧义询问时的能力探测

决定：用户选择 A（2026-10-22）。询问前对候选做只读探测并标注（可访问/只读/无权限/授权失效，超时不阻塞）；探测结果不参与自动选择；无权限候选不隐藏；--no-probe 可跳过。已入 design.md §5。

## Q3：resolve 输入契约与无品牌证据输入

决定：用户确认三点（2026-10-22）：v1 支持 URL、同构异域链接（doubao.com 等）、裸 token，纯自然语言描述不进 v1（Agent 追问）；品牌内/全局唯一绑定直接选中（sole，按存在性判定，失效则报修复授权不换绑定）；无品牌证据且多候选时 pins → 询问并 pin，不做默认 feishu 猜测。算法已更新 design.md §5。

## Q2：首版是否必须支持同一应用的多个用户

场景：公司已审批一个应用，同事 A、B 都希望授权它；如果绑定仅对应 CLI profile，profile add 的 App ID 唯一限制会阻止这种模型。

选项 A：首版每个绑定使用不同 App ID，复用正式 profile 接口，接受新增账号可能需要新增应用与管理员审批的成本。
选项 B：首版必须支持同一应用多个用户，先核查逐请求用户选择能力；没有稳定入口则重新评估执行后端，不能用全局切换用户模拟并发隔离。

建议：A 适用于个人首版且可接受多应用；B 适用于同公司多人复用一个应用的核心需求。不支持同应用多用户的限制必须在产品中明确展示。

决定：用户选择 A（2026-10-22）。绑定与 profile 一一对应，不做 C 的抽象层；约束已固化到 ADR-0001。
